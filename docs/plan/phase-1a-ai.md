## 1. The three rules every card carries

**Rule 1 - Answer or refuse, never guess.** The model never writes a
fact, a number, a date, or a sentence a student reads. It only selects
which verified records apply. Every sentence is generated by code from
the record's own fields (`app/ai/grounding.py`, already built and tested
this way). If no published, fresh, non-synthetic record answers the
question, the answer is "not verified" - not "probably", not "it may be",
not a range the model made up. A banned-phrase guard runs over every
template string, every i18n string and every prompt text: `maybe`,
`probably`, `might`, `likely`, `I think`, `should be`, `शायद`,
`ho sakta hai`, `guarantee`, `not suited`, rank language, personality
labels. It is a unit test, so it fails the build, not a review note.

**Rule 2 - Two verifications on every AI call, then code.** Each runtime
answer costs exactly two model calls, reserved atomically as a pair:

1. **Selection pass.** The model returns bare record ids from the
   retrieved set, or `NOT_GROUNDED`.
2. **Verification pass.** A second call with a different, adversarial
   prompt: for each id from pass 1, and only those, "does this record
   directly answer the question - `YES <id>` or `NO <id>`". Anything
   not answered `YES` in pass 2 is dropped. If pass 2 drops everything,
   or returns anything outside the strict format, the whole answer is
   `insufficient_information`.
3. **Code validation** on both passes: exact line format, every id in
   the retrieved set, publication status re-checked, freshness checked,
   then fixed-template sentences with citations.

Both passes' ids (never text) are written to `ai_usage`. Reviewer-facing
calls follow the same shape: an extraction pass, a verification pass
that checks each proposed value against the source text, a mechanical
verbatim-substring check, and then the human maker-checker. Hindi
drafts: a translation pass, a back-translation check pass, then the
Hindi reviewer. Nothing reaches a student or a published row on one
model opinion.

**Rule 3 - Free tier, so nothing personal ever leaves.** The pilot runs
on the Gemini free tier. Free-tier prompts may be used by the provider
to improve its products (the owner confirms the current terms in AI-10
and records them). Therefore, enforced by a test, not policy: an
outbound payload contains only a template id, record ids and their
published values, and a language code. **No student-typed text, ever,
in Phase 1a** - the optional 200-character follow-up field is not built
until (a) the distress rule (CONSENT-7) exists and (b) the owner moves
to a paid tier with a no-training clause. A provider `429` or quota
error is treated exactly like a cap hit: deterministic fallback, no
retry, no second provider. The daily request budget is set to at most
half the provider's published daily free limit, because each answer
costs two calls; the owner writes the current limit on the AI-10 card.

1. Every AI card owns only `app/ai/*`, new files, its own tests and
   append-only i18n keys (section 4C). No Phase 1 file is edited; the
   three journey-template call sites for `ask_bcion` already exist.
2. Each green AI branch merges to `main` as soon as the lead has re-run
   the suites - **not** held on a long-lived `phase-1a` branch. With
   `AI_ENABLED=false` (the default everywhere) the only visible change is
   the deterministic Ask page, which the build pack requires anyway.
   Phase 1 testers, CI and staging see no model call and no behaviour
   change. A long-lived branch was considered and rejected: it only adds
   a big-bang merge at the end for no extra isolation.
3. "Adding it to Phase 1" = the Phase 1a exit gate (section 9) passes,
   then AI-12 flips the flag on staging with the kill-switch drill. One
   line in the environment, no code change, reversible in one line.

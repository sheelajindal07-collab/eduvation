## What to build
`app/ai/retrieval.py` (new): given a pathway id, career id or claim id, fetch only claims whose `status == published` and whose backing source is not `SourceType.synthetic` - re-check both conditions in Python even when called with a reviewer-scoped client, do not rely on RLS alone (the same "never trust a caller blindly" principle already applied in `app/planning/comparison.py`'s `field_value_for()` and `app/api/eligibility.py`'s `_criteria_from_claims` - read those two functions for the exact pattern, they are not in your owned list but you may read them). Flag any claim past its freshness SLA using the same constant and comparison `app/ai/grounding.py` already uses (`DEFAULT_FRESHNESS_SLA_DAYS`, imported from `app.planning.comparison` - do not invent a second staleness rule). For a pathway or career, also call the existing `app/rules` cost, timeline and eligibility functions to compute derived numbers (do not duplicate their arithmetic here - call them). Reuse `app.planning.comparison.field_value_for` and its `safe_source_url` helper rather than writing new equivalents. Emit compact record objects carrying a server-assigned short id (the actual claim id is fine to use directly, or a shortened deterministic form if `app/ai/schemas.py`'s `MAX_ID_CHARS` demands it - check that constant), the field name, the value, the source authority and URL, and a staleness flag.

This module must import nothing from `saved_plans`, `student_profiles`, `guest_session`, or any other student-identity-bearing table or module - it only ever reads career/pathway/claim/source data. Write an explicit test that inspects this module's own import statements (or its compiled bytecode's referenced names) and fails if any forbidden name appears, rather than trusting a human read to catch it later.

# BCI-024 - AI-4 follow-up: close the account identity-hash oracle in ai_reserve/ai_budget_remaining

Model tier: strongest
Wave: P1a (urgent security follow-up, 2026-09-22) - Phase 1a runs alongside Phase 1; this card touches no Phase 1 file
Worktree: phase1a/ai-15-identity-hash-fix

## The finding (verified by the lead directly against the merged code before this card was written - do not re-derive, just fix)
`db/migrations/0011_ai_usage.sql`'s `ai_reserve(p_identity_kind, p_identity_hash, p_template_id, p_calls)` and `ai_budget_remaining(p_identity_kind, p_identity_hash)` are both `SECURITY DEFINER`, both granted `execute` to `anon`, and both take `p_identity_hash` as a plain caller-supplied argument with **no check that it actually matches the calling session's own identity**. `ai_identity_hash(text) -> text` (also anon-granted) is a pure, unpeppered `sha256` of whatever text it is given - deterministic, no secret involved.

For `identity_kind = 'guest'` this is fine by design: `app/ai/budget_db.py`'s `for_guest()` hashes the guest's own opaque, server-generated session token (`app/web/guest_session.py`'s `create_guest_session()` RPC) - possessing that token (from your own httponly cookie) IS the credential, so a caller who can compute its hash already had to have the token.

For `identity_kind = 'account'` this is a real, reproduced exposure: `for_account()`'s own docstring says `account_id` "is the same value `auth.uid()` returns" - a Supabase Auth user id, which is **not a secret** (it is returned to the owning user in ordinary API responses and is a UUID, not a token). Any anon-key caller can call `ai_identity_hash(<any known or guessed account uuid>)` themselves, then pass that hash to `ai_budget_remaining('account', <hash>)` to read a stranger's remaining AI budget, or to `ai_reserve('account', <hash>, ...)` to burn a stranger's per-identity daily cap - reproduced live: `ai_budget_remaining` returns a real number for an arbitrary uid with no session at all. `ai_settle` is NOT part of this finding - it takes an opaque reservation `uuid` the caller must already hold, a different (already-documented, already-accepted, `docs/DECISIONS.md` 2026-09-22) residual risk class, not this one.

Practical exposure today is nil (`AI_ENABLED` is false everywhere, no real usage exists), but this must be closed before AI-12 ever flips the flag on staging, and the owner is applying migrations toward production on a schedule that assumes this closes promptly - treat this as time-sensitive, not routine.

## What to build
`db/migrations/0015_ai_identity_binding.sql` (additive, `create or replace function` on the same two functions - the established pattern for a definer-function fix, exactly what `0014_account_active_grant_fix.sql` already did for the same oracle *class* on `account_active()`; read that file first for the house style and its own revert-to-prove test file, `tests/db/test_account_active_oracle.py`, for the pattern to match here). Both `ai_reserve` and `ai_budget_remaining`:

- When `p_identity_kind = 'account'`: **ignore whatever `p_identity_hash` the caller sent** and derive the real hash from `ai_identity_hash(auth.uid()::text)` instead, inside the function body. If `auth.uid()` is null (no session at all, i.e. a genuinely anonymous caller), raise the same `BCAI3` malformed-call error the function already uses for other validation failures - an anonymous caller has no account identity to bind to at all, so this is not a new error class.
- When `p_identity_kind = 'guest'`: **unchanged** - keep trusting the caller-supplied `p_identity_hash`, since a guest's own token possession is the credential and there is no `auth.uid()` for a guest session to bind to instead.
- Do not touch `ai_settle`, `ai_identity_hash`, `ai_usage`, `ai_usage_caps`, `ai_usage_daily_totals`, or any grant not already listed above - this is a narrowly scoped fix, not a redesign.

Revert-to-prove tests, in the style of `tests/db/test_account_active_oracle.py`: (1) with the fix in place, an anon-key client calling `ai_budget_remaining('account', ai_identity_hash('<a real other account's auth uid>'))` gets EITHER an error (no session) or, if called as a different signed-in account, its OWN budget, never the named victim's; (2) temporarily reverting to the old unbound behaviour (comment out the `auth.uid()` derivation, restore trusting the caller's hash) makes an equivalent test fail, proving the test actually catches the class of bug being fixed, then restore and show it passes again; (3) the guest path is unaffected - an existing or a new test proves a guest's own `remaining()`/`reserve()` still works exactly as before, unhashed-identity-swap included as a negative case (a guest cannot spoof another guest's token-derived hash either, but that was already true before this fix and should stay true).

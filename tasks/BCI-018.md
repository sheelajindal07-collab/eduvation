## What to build
`app/api/ask.py` and `app/web/ask_pages.py` already exist (UI-11/BCI-014, merged) and currently run deterministic-only, deliberately built before `app/ai/pipeline.py` existed. `app/ai/pipeline.py` (AI-6) is now merged - read it directly (`answer(db, request, provider, budget, *, as_of=None) -> Answer`, `app/ai/schemas.py`'s `AskRequest`/`Answer`/`AIAnswerStatus`) rather than guessing its shape.

**The deterministic fact-card baseline never goes away.** `ask.py`'s existing `assemble_ask_answer()` (built on `app.planning.comparison.field_value_for`) is what makes the page work with AI off, and it must keep working exactly as it does today, unconditionally, on every request - this is the whole reason UI-11 was built deterministic-first. Do not make fact cards depend on the pipeline succeeding.

**The pipeline is an additive layer, not a replacement.** When `Settings.ai_enabled` and `Settings.ai_configured` are both true, also call `pipeline.answer(db, request, provider, budget)`:
- If the returned `Answer.status == AIAnswerStatus.answered`, render its `sentences` and `citations` **above or alongside** the existing deterministic fact cards from `assemble_ask_answer()` - never in place of them.
- For every other `Answer.status` (`not_available`, `insufficient_information`, `ai_unavailable`, `budget_exhausted`, `unsupported_template`) - which is what happens on the AI-disabled path too, since `pipeline.answer()` returns `ai_unavailable` *before retrieval* when the flag is off, with no fact cards attached at all - render nothing extra. The page falls back to exactly what it already rendered before this card: the deterministic fact cards plus `docs/UI.md`'s exact copy, unchanged. Never a blank page, never an error, never a second, conflicting message.
- When `ai_enabled`/`ai_configured` is false, do not call `pipeline.answer()` at all - the deterministic path alone is the whole response, exactly as UI-11 left it.

**Provider and budget, both real but injected, not constructed per-request.** Construct one process-local `AIRequestBudget` (via `app/ai/budget.py`'s existing `default_budget()` or equivalent - read the file for the real name) as a module-level singleton in `app/api/ask.py`, the same lifecycle pattern `app/core/config.py`'s `get_settings()` uses (`lru_cache`) - a fresh budget object per request would defeat the whole point of a daily cap. Construct a real `app.ai.gemini_provider.GeminiProvider()` only when actually about to call the pipeline (inside the AI-enabled branch, not at import time) so an unconfigured environment never raises at import - `GeminiProvider()` already raises `GeminiNotConfiguredError` if the key is missing (read `app/ai/gemini_provider.py`), which this route must catch and treat exactly like `ai_unavailable`, not let escape as a 500.

Identity for the budget/cap: use the same identity resolution `app/web/guest_session.py`/the JWT-based account lookup already establish elsewhere in this codebase (an account id when a bearer token is present, else the guest-session id) - read how an existing route derives this, do not invent a new identity scheme.

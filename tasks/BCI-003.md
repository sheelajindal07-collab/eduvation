# BCI-003 — M2 eligibility, cost and timeline engines

**Milestone:** M2 · **Status:** eligibility, cost and timeline engines
done; cost engine wired live into `GET /compare`; reservation/quota not
started

## Scope (Lite Build Pack §6)
"Eligibility returns three outcomes. Meets the checked criteria; does
not meet the checked criteria; insufficient information, review
required. An unknown domicile rule or missing subject requirement never
becomes a rejection. Rule functions are reviewed, versioned and cite
their source."

## What shipped (2026-09-19)
- `app/rules/eligibility.py`: a composable criterion engine.
  `EligibilityInput` holds the optional, separately-consented facts
  eligibility needs (age, marks %, subjects studied, domicile, category)
  — deliberately kept out of the minimal `StudentProfile`
  (docs/DATA.md "Minimisation"). Five reusable criterion builders
  (`minimum_age`, `maximum_age`, `minimum_marks_percentage`,
  `required_subjects`, `domicile_in`), each citing an optional
  `source_claim_id` and carrying an explanation string — never a bare
  boolean, per docs/UI.md ("name the missing requirement, never guess").
- **Combination priority, made explicit and tested**: `does_not_meet` >
  `insufficient_information` > `meets`. A definite failure on one
  criterion is never masked by an unrelated unknown on another — the
  student sees the real blocker, not a vague "unknown" that happened to
  be checked first.
- **23 new tests** (`tests/unit/test_eligibility.py`), organised so the
  priority-combination logic gets its own dedicated test class rather
  than being implied by the individual-criterion tests: every criterion
  tested at its exact boundary (age = minimum passes, marks % =
  threshold passes), every criterion's "unknown" path tested
  separately, and — the case that actually matters — a realistic
  NEET-UG-shaped composition (age 17–25, PCB required, 50%+ marks)
  tested end to end for an eligible student, a student missing one
  required subject, and a brand-new student who's only completed the
  minimisation-scoped quick start (nothing eligibility-relevant filled
  in yet) — correctly `insufficient_information`, not a silent
  rejection.
- 57 tests passing total (44 unit + 13 live DB), lint/typecheck clean.

## Cost engine (2026-09-19)
- `app/rules/cost.py`: four amounts that never merge.
  - `verified_charges` — **summed** from possibly-multiple fee-component
    claims (tuition, hostel, exam fee, ...), reusing
    `app/planning/comparison.py`'s trust-labelling. If any expected
    component is `not_available`, the total is `None` — never a
    silently-partial sum presented as the complete cost. Flags `stale`
    separately when every component has a value but at least one needs
    rechecking.
  - `estimated_additional_expenses` — a stated assumption, never a claim.
  - `confirmed_assistance` — scholarships/loans actually awarded; the
    **only** amount that reduces `net_to_arrange`.
  - `potential_assistance` — eligible-but-unawarded; shown for
    awareness, **never subtracted** (Lite Build Pack §6: "an unawarded
    scholarship is never subtracted" — the core safety rule of this
    module, tested explicitly and separately from the "they stay
    separate" test).
- **10 new tests** (`tests/unit/test_cost.py`): boundary cases (zero
  cost, no components at all), the missing-component-never-silently-
  drops-cost case, the stale-but-still-summed case, and three variations
  on confirmed vs. potential assistance to make sure they can never be
  swapped or merged by accident.
- 67 tests passing total (54 unit + 13 live DB), lint/typecheck clean
  first try on both.

## Timeline engine (2026-09-19)
- `app/rules/timeline.py`: stages sum to a total that's honest about two
  separate failure modes.
  - **Unknown duration** — mirrors `cost.py`'s `sum_verified_charges`
    deliberately: any stage (required or optional — a display-only
    distinction here) with `duration_weeks=None` makes `total_weeks`
    `None`, never a partial sum shown as the real timeline.
  - **Overlap, not blind addition** (§6: "preparation, applications and
    internships overlap") — `overlap_weeks_with_previous` on a stage is
    subtracted from the naive sum. An overlap longer than either
    adjacent stage's own duration raises `ValueError` — that's a
    content-authoring error to catch in tests, not a student input to
    silently clamp.
  - `expand_attempts()` builds one `Stage` for "user-chosen attempts"
    (§6) — N attempts with a gap between them, never a trailing gap
    after the last attempt.
  - `ParallelActivity` (§6: "parallel activities") is visible on the
    result but categorically excluded from `total_weeks` — same shape
    as `cost.py`'s potential-assistance guarantee.
  - `BackupPathway` (§6: "backup transitions") is just a name plus its
    own stage list; its timeline is computed by the same
    `compute_timeline()`, so a backup never shares arithmetic with the
    primary path it's an alternative to.
- **21 new tests** (`tests/unit/test_timeline.py`): the unknown-duration
  guarantee (required and optional stages alike), overlap boundary cases
  (`docs/SECURITY.md`'s listed "overlapping durations" and "rounding"
  gates — including overlap exactly equal to the shorter stage, and
  overlap exceeding either stage), attempt expansion (zero/negative
  attempts rejected, gap applied only between attempts), and parallel
  activities/backups never entering the total.
- 88 tests passing total (75 unit + 13 live DB), lint/typecheck clean.

## Cost engine wired into GET /compare (2026-09-19)
- `app/planning/comparison.py::assemble_cost_summary()`: runs
  `app/rules/cost.py`'s real arithmetic — including `net_to_arrange` —
  over the same claims `assemble_cost_breakdown` already displays.
  Deliberately the conservative first wiring, not a schema change:
  `verified_charges` stays the single already-verified claim a content
  reviewer publishes (docs/DATA.md "Cost engine"), passed through
  `sum_verified_charges` as a one-component list, rather than switching
  content authoring over to itemised fee components (tuition/hostel/exam
  fee separately) — that itemisation is real future work but is a
  content-workflow decision this task doesn't make unilaterally.
- **"Assumption editing"** (Lite Build Pack §6, docs/UI.md) landed for
  real: `GET /compare?...&estimated_additional_expenses=<value>`
  overrides the estimate for that one request only — never persisted,
  never a Claim. Omit it and the pathway's
  `estimated_additional_expenses_hint` claim is used, or 0.0 if it has
  none (an omitted assumption means "assume nothing extra", not
  "unknown").
- `potential_assistance_not_yet_awarded` becomes at most one
  `AssistanceItem`, omitted (not zeroed) when the claim is
  `not_available`. There is still no `confirmed_assistance` source —
  that's student-specific award data that doesn't exist before M3's
  sign-in/consent work — so `net_to_arrange` today is verified + estimate
  with nothing confirmed subtracted, and `potential_assistance` is never
  part of that number.
- Fixed a real circular import surfaced by this wiring:
  `app/planning/comparison.py` now imports `app/rules/cost.py`, which
  already imported `FieldValue` back from `comparison.py` for one type
  annotation. Deferred that import under `TYPE_CHECKING` in `cost.py` —
  safe because `cost.py` already has `from __future__ import
  annotations`, so the annotation is never evaluated at runtime. No
  behaviour change; verified via `python -c "import app.main"` plus the
  full test suite.
- **9 new unit tests** (`tests/unit/test_comparison.py`): the wiring
  itself (net = verified alone with no hint/override; missing verified
  charges gives `None` net, not a guess; hint used when no override;
  override replaces the hint for one request; no hint/override assumes
  zero, not unknown), plus the money-safety property carried over from
  `test_cost.py` (potential assistance visible but never reduces
  `net_to_arrange`; no potential claim gives an empty list, not a zero
  item; confirmed assistance is always empty in this slice, documented
  and tested rather than just implied).
- **1 new live-DB test**
  (`tests/db/test_api_explore_compare.py::test_net_to_arrange_is_computed_live_and_assumption_is_editable`):
  seeds a real published `verified_charges` claim, confirms `GET
  /compare` returns the real computed `net_to_arrange` (not just the raw
  claim value), confirms the query-param override changes it for that
  request, and confirms a *different* pathway in the same request with
  no published claim still comes back with `net_to_arrange: null` — the
  override never papers over a genuinely missing figure.
- 92 tests passing total (83 unit + 18 live DB — the extra 5 live-DB
  tests over the 13 recorded earlier this session belong to another
  concurrent session's in-progress eligibility-endpoint wiring, not this
  change; see STATUS.md's concurrent-sessions note), lint/typecheck clean.

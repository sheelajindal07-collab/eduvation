# BCI-026 - Wire the database-backed AI budget into the live Ask BCION routes

Model tier: strongest
Wave: P1a (audit follow-up, 2026-09-23) - Phase 1a runs alongside Phase 1; this card touches no Phase 1 file
Worktree: phase1a/ai-budget-wiring

## The finding (verified by the lead directly before this card was written)
`db/migrations/0011_ai_usage.sql` (AI-4) and `db/migrations/0015_ai_identity_binding.sql` built a real, per-identity, database-backed spend cap - `app/ai/budget_db.py`'s `AIRequestBudgetDB`, with `ai_reserve()`/`ai_settle()`/`ai_budget_remaining()` enforcing per-identity daily, global daily and global monthly ceilings, hardened last night against a cross-account oracle. **None of it is actually used.** `app/api/ask.py`'s `_ai_budget()` (and `app/web/ask_pages.py`, which reuses the same helper) construct exactly one `lru_cache`d `app.ai.budget.AIRequestBudget` - a single process-wide, in-memory, non-identity-keyed daily counter - shared by every `/ask` and `/ask/view` request from every account and every guest combined. Today, one account issuing many requests is capped by literally the same counter as every other student put together, with no persistence across a restart and no ledger row ever written to `ai_usage`. `scripts/ai_spend_report.py`/`app/ai/alerts.py` (AI-13) therefore currently have no live data feeding them at all.

Practical exposure today is nil (`AI_ENABLED` is false everywhere), but this must be fixed before `AI-12` ever flips the flag on staging - the whole point of building AI-4 was per-identity, cross-worker-safe spend accounting, and right now the app doesn't have it.

## What to build
Replace `app/api/ask.py`'s `_ai_budget()` singleton with real per-request identity resolution feeding a real `AIRequestBudgetDB` instance, used by both the JSON route (`ask()`) and, via the same helper, `app/web/ask_pages.py`'s `ask_page()`:

1. **Account identity**: when a valid `Authorization: Bearer <token>` header is present, resolve the account id via `session.client.auth.get_user(jwt=...)` - the exact, already-established pattern `app/api/plans.py`'s `_current_user_id()` uses (read it directly, copy the pattern, never decode a JWT client-side). Construct `AIRequestBudgetDB.for_account(account_id, template_id=..., client=<the same RLS-scoped client the request already has>)`.
2. **Guest identity**: when no bearer token is present, resolve (or, if none exists yet, establish) the guest-session token via `app/web/guest_session.py` (read `token_from_request`/`ensure_session`/`create_session` directly - these routes have never needed guest-session awareness before, so you are extending, not copying, an existing pattern here; make a real, documented judgment call about whether `/ask`/`/ask/view` should mint a new guest session for a visitor who has none, or fall back gracefully to the current global in-memory budget for that one edge case only - either is defensible, but state which you chose and why). Construct `AIRequestBudgetDB.for_guest(session_token, template_id=..., client=...)`.
3. **Neither resolvable** (should not normally happen if #2 mints a session, but handle it explicitly rather than crash): fall back to the existing global `AIRequestBudget`, exactly as today - never a 500, never an unhandled exception.
4. The two-call reservation shape (`reserve()`/`remaining()`) that `app.ai.pipeline.answer()`/`app.ai.what_changed.answer_what_changed()` already expect must not change - `AIRequestBudgetDB` is already a drop-in per its own docstring; confirm this holds rather than assuming it, since it has never actually been exercised end-to-end through a real route before.
5. A budget-construction failure (e.g. the account/guest lookup itself raising) must degrade to `AIAnswerStatus.ai_unavailable`, the same way a `GeminiNotConfiguredError` already does in this file today (read that existing handling for the pattern) - never a 500, never silently falling through to the global budget in a way that masks a real auth problem.

**Do not change** `app/web/reviewer/extract.py`'s own budget handling - that one is intentionally per-reviewer via a separate in-memory dict (AI-14's own card said so explicitly), a smaller, already-correct, separate design; this card is scoped to the two student-facing routes only.

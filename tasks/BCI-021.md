# BCI-021 - AI-18: Next-steps template over a server-owned, claim-bound action catalogue

Model tier: standard

Worktree: phase1a/ai-18-next-steps

## What to build
`app/ai/actions.py` (new): a server-owned catalogue of candidate next-action templates, each computed **in code, by inspecting published claims** for a pathway (or a saved plan's pathways) - e.g. a claim with a deadline-shaped field produces "register before `<date, taken straight from the claim>`"; a claim naming a required document produces "collect `<document, from the claim>`". Every candidate action must cite the specific claim id it was derived from - no action text exists that was not built this way. The model's role, via the same two-pass selection/verification shape `app/ai/pipeline.py` already establishes (read it directly - reuse `app.ai.pipeline.answer()`'s two-call pattern and `app.ai.guards`' validation helpers rather than writing a third parallel implementation), is only to **select and order** which of the already-computed candidate ids are most relevant to the request - it never authors an action's text.

Add a new template `next_steps` to `app/ai/prompts.py`'s `TEMPLATE_REGISTRY` (read that file directly for the exact `PromptTemplate` shape and how `pathway_overview`/`cost_breakdown`/`eligibility_gap` are already defined - follow the same pattern) requiring either `pathway_id` or a `plan_id` (read `app/ai/schemas.py`'s `AskRequest` - `plan_id` is already one of its fields, unused by any template until now). When `plan_id` is given, resolve it through the **existing** plans API functions (`app/api/plans.py` - read `list_plan_actions`/`save_plan`/the ownership check pattern; do not add a new database read path) so a guest's plan resolves by guest-session id and a student's by JWT-derived account id, exactly like every other plan-scoped route already does - never trust a bare `plan_id` in the request without that ownership check, since a request could name another identity's plan id.

Wire `next_steps` into `app/api/ask.py`'s `ASK_TEMPLATES`/route so `GET /ask?template=next_steps&pathway_id=...` (or `&plan_id=...`) works end to end, reusing `_pipeline_answer()`'s existing additive-layer pattern (read it directly - do not duplicate its AI-enabled/budget/provider-construction logic, call the same helper). A student B's plan id must return 404 for student A and for a guest, exactly like the existing plans API already enforces.

## What to build
A reviewer-only page at `/reviewer/extract` (new router file `app/web/reviewer/extract.py`, `APIRouter(prefix="/reviewer", tags=["reviewer-console"], include_in_schema=False)` matching the exact pattern `app/web/reviewer/queue.py` already uses - read that file for the auth-dependency pattern, do not invent a new one) where a signed-in reviewer pastes the plain text of an official document plus picks an existing source (by id, from a dropdown/select populated the same way `app/web/reviewer/claims_forms.py` already populates its own source picker - read it, reuse the pattern). No fetching, no URL input, no crawling - manual paste only, matching the build pack's "manual document intake first."

`app/ai/extraction.py` (new): given the pasted text and a small fixed target field list (reuse whatever field names this codebase's claim conventions already use - `minimum_age`, `verified_charges`, `fee_component:<name>`, the `stage:<order>:*` timeline convention, etc.; do not invent new field names), run an **extraction pass**: one `provider.generate(...)` call asking the model to propose `field, value, quoted_span` triples, one per line in a strict format you define (e.g. `FIELD|VALUE|QUOTED_SPAN`), or nothing if the text contains no extractable facts. Then a **verification pass**: a second, separate `provider.generate(...)` call, adversarially framed, asking for each proposal: is `value` stated verbatim inside `quoted_span`, and is `quoted_span` an exact substring of the original pasted text - `YES <n>` or `NO <n>` per proposal, nothing else. Then, in code (never trusting the model's own verification answer alone): mechanically re-check that `quoted_span` is an exact, case-sensitive substring of the original pasted text, and that `value` is a substring of `quoted_span` - drop any proposal that fails either check, or that pass 2 marked `NO`, or that pass 2's response violates the strict format (whole-response rejection, same all-or-nothing rule the rest of Phase 1a uses). Use `app/ai/gemini_provider.py`/`app/ai/adapter.py`/`app/ai/mock_provider.py` (all merged - read them for the real interface, do not guess) for the provider calls, and `app/ai/budget.py`'s in-memory budget for the two-call reservation, keyed on the reviewer's own identity. The pasted text itself is never logged and never stored beyond the request - it exists only in memory for the duration of one request.

Surviving proposals pre-fill `app/web/reviewer/claims_forms.py`'s existing claim-creation form (do not duplicate that form - render your own page's results as a set of pre-filled links/forms that POST to the **existing** `POST /claims` API route, `app/api/claims.py`'s `create_claim`, with `extracted_by="ai"` and `status` left to default to `draft` as that route already enforces server-side). You are not adding a new database write path - every write still goes through the existing, already-tested claims API and its existing maker-checker enforcement. A reviewer must still review and submit/approve each draft exactly as with a manually entered claim; this page only pre-fills the form, it never auto-submits.

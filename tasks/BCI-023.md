## What to build
`scripts/ai_spend_report.py` (new): a read-only, owner-run script querying the `ai_usage_daily_totals` reviewer-only view and the `ai_usage_caps` row (both in `db/migrations/0011_ai_usage.sql`, merged - read that file directly for the real column names and the view's exact shape, do not guess) through `app.ai.budget_db.AIRequestBudgetDB`'s `for_account`/`for_guest` constructors or a plain reviewer-scoped Supabase client (read `app/ai/budget_db.py` directly for the real method names - `remaining`, `reserve`, `reserve_usage`, `settle`). Reports, for a given date range: total calls reserved vs settled, the fallback rate (answers that resolved to anything other than `AIAnswerStatus.answered` - read `app/ai/schemas.py` for the exact enum values), spend against each of the three caps (per-identity, global daily, global monthly - the row shape `ai_usage_caps` already defines), and requests per identity-hash bucket (never a raw identity - `ai_usage.identity_hash` is already a digest, never reverse it). **No claim or answer content is ever read or reported** - the table this queries has no such column at all, so this is a structural guarantee, not a filter you have to get right.

Two-pass disagreement isn't directly recorded by `ai_usage` (only `selection_ids`/`verification_ids` per settled row) - compute it from those two columns: the fraction of settled, non-empty-selection rows where `verification_ids` is a strict subset of `selection_ids` (i.e., the verification pass dropped at least one id the selection pass proposed). Document this derivation clearly in the script's own docstring, since it is inferred, not a stored metric.

`app/ai/alerts.py` (new): given a spend report (or queried fresh), fires **one notice per threshold** (50%, 80%, 100% of the daily cap; same three thresholds for the monthly cap - six threshold/cap combinations total) through the existing `app.notifications.factory.get_email_sender()` (`app/notifications/sender.py`'s `EmailSender` protocol, already merged - read both files directly, do not add a new notification channel). **Not n8n** - n8n is not deployed for this pilot (`docs/DECISIONS.md`, already settled; you do not need to re-read that file, just don't build toward n8n). "Once per threshold" means: track which thresholds have already fired for the current UTC day/month (a small in-memory or file-based marker is fine for this pilot's scale - state your choice and why) so a script run every few minutes doesn't re-send the same notice repeatedly.

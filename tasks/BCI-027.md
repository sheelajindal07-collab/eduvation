# BCI-027 - Real per-request banned-phrase scan over generated answer sentences

Model tier: standard
Wave: P1a (audit follow-up, 2026-09-23) - Phase 1a runs alongside Phase 1; this card touches no Phase 1 file
Worktree: phase1a/ai-banned-phrase-runtime-scan

## The finding (verified by the lead directly before this card was written)
`docs/ARCHITECTURE.md` used to claim "the banned-phrase guard runs over the result" as part of the pipeline's per-request code validation (now corrected - read the fixed text for the accurate description). The reality: `app/ai/guards.py`'s `assert_no_banned_phrases()` is called exactly once in the whole codebase, from `app/ai/prompts.py`, at **import time**, over the fixed `TEMPLATE_REGISTRY` label strings only - "What will this cost?" and its four siblings. `app/ai/pipeline.py`'s step 11 generates `Answer.sentences` from a published claim's own `.value` field (`fact_sentence_for_record`) and step 13 returns that `Answer` with no scan at all over the generated text.

This means: if a published, reviewer-approved claim's *value* happens to contain hedge, guarantee or rank language (a human content error at review time, not an AI hallucination - the two-pass pipeline correctly never invents anything), the current pipeline renders it to a student completely unscanned. Maker-checker review is supposed to catch this at source, but this pilot's own design already treats the banned-phrase list as a mechanical backstop everywhere else it appears (fixed strings, the eval set's own calibration fixtures) - the one place it was documented as covering runtime-generated content was never actually wired to do so.

Practical exposure today is nil (`AI_ENABLED` is false everywhere), but this is exactly the kind of defense-in-depth gap that should close before the flag is ever turned on.

## What to build
A new function in `app/ai/guards.py` - do not reuse `assert_no_banned_phrases()` as-is, since its contract is "raise immediately, this is a build-time bug" (correct for the fixed-string case, wrong for runtime content: a real request must never crash on this, it must degrade gracefully like every other failure mode in this pipeline). Something in the shape of `scan_generated_sentences(sentences: Sequence[str]) -> tuple[str, ...]` (your naming call, document it) that runs `app.ai.schemas.find_banned_phrases()` over each generated sentence and returns which phrases were found, if any - pure, no raising.

Wire this into `app/ai/pipeline.py`'s `answer()` between step 11 (sentence generation) and step 13 (the final `answered` return): if any generated sentence contains a banned phrase, the answer must **not** be returned as `answered` - degrade to `AIAnswerStatus.insufficient_information`, the same all-or-nothing downgrade shape steps 9 and 10 (empty intersection, staleness) already use, with `citations` still populated the same way the staleness case already does (so a caller can see which record blocked the answer, per that step's own precedent - read it directly). Do the same for `app/ai/what_changed.py`'s equivalent final-render step (its own `RenderedDiffLine.text` generation) - read that module's structure first; it has its own separate render function, not a call into `pipeline.py`.

**This is a real, user-facing safety degrade, not a cosmetic addition** - write it with the same rigor as the rest of this pipeline: a claim value deliberately seeded with a banned phrase in a test must be proven to downgrade the *whole* answer, never partially redact just that one sentence (matching this pipeline's existing "reject whole, never partial" philosophy throughout - re-read the module docstring's own stated design principle before writing this).

Do not change `BANNED_PHRASES` itself, `find_banned_phrases()`, or `assert_no_banned_phrases()`'s own existing call site and behaviour (the import-time check stays exactly as it is - this card adds a second, independent runtime check, it does not replace or weaken the first one).

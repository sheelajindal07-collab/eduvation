## Read this first - a real mismatch between the eval set and the pipeline
`evals/ask_bcion_questions.yaml` (AI-9, merged) was written with a `text` field per question, "the question, exactly as a student might type it" - but `app/ai/pipeline.py`'s `answer()` (AI-6, merged) takes an `app.ai.schemas.AskRequest`, which has **no free-text field at all** (`template_id` plus one of `pathway_id`/`career_id`/`claim_id`, and `lang` - read `AskRequest` directly). This is not a bug in either card; it is Rule 3 working as intended (no student-typed text ever reaches the provider) colliding with an eval set that was written to read naturally for a human. Your job in this card includes resolving this mapping, not assuming it away:

For each question, choose the one `template_id` from `app/ai/prompts.py`'s `TEMPLATE_REGISTRY` (`cost_breakdown`, `pathway_overview`, `eligibility_gap`) that best matches the question's evident intent (a fee question -> `cost_breakdown`, an age/requirement question -> `eligibility_gap`, a general "what does this involve" question -> `pathway_overview`), and build the `AskRequest` from the question's own `synthetic_record_ids` (the first pathway-shaped id for `pathway_id`, or claim-shaped id for `claim_id`, depending on the template's `PromptTemplateRequirement`). Document this mapping as a table or a function, not scattered inline guesses - a future card or the owner needs to be able to see and adjust it. The question's own `text` field becomes a human-readable label in the report, not something sent to the provider or the pipeline - state this plainly in the script's own docstring so nobody later assumes it is.

## What to build
`scripts/run_ai_eval.py`: reads `evals/ask_bcion_questions.yaml`, maps each question to an `AskRequest` per the above, runs it through `app.ai.pipeline.answer()` with an injectable provider (`--provider mock` using `MockAIProvider`, always used in tests/CI; the real `GeminiProvider` only for an owner-run live pass, never exercised in a test) and a budget with a **hard call ceiling** (`--max-calls N`, default something conservative) that aborts the whole run, not just skips a question, the instant the next question would exceed it - reporting which questions were not reached. Writes a JSON report (per question: id, category, mapped template_id/entity_id, `Answer.status`, whether it matched `expected_status`, `selection_ids`, `verification_ids`, latency, call count; a run-level summary: totals, spend/call count against the cap, p95 latency) to `evals/reports/<run-date>.json` - no student data, this is entirely synthetic input either way.

`category: injection` questions need their `synthetic_record_ids`' backing claim *values* to actually contain the injection text described in the question's `notes` (an `injection_vector: record_text` case) or the mapped `AskRequest` needs no special handling at all (an `injection_vector: user_question` case is moot here, since there is no user-question field reaching the pipeline - flag this explicitly in your report rather than silently dropping the category's coverage).

`category: api_failure` questions (`force_provider_error: true`) must be run with the injected provider scripted to raise (via `MockAIProvider.raise_on_call`, already merged - read it) rather than against the real provider, even in a "live" run - the point is proving the pipeline's own fallback behaviour, not testing the real API's uptime.

**A companion synthetic seed**, so a live run has real data to answer against: extend or companion-script alongside `scripts/seed_synthetic.py` (read it for the existing synthetic-fixture convention and the `--purge` counterpart - do not remove or weaken its production-ref guard) to insert real rows on the local stack for the eval set's `synthetic_record_ids`, shaped to make each category's `expected_status` plausible against real data (a `stale` category question needs a real claim whose `verification_date` is actually past the freshness SLA; a `source_mismatch` case needs a real id that resolves to an unrelated record; etc.). This can be a second file (`scripts/seed_ai_eval_fixtures.py`) if that keeps `seed_synthetic.py` untouched and simple - your call, state which you chose and why.

If full live-data coverage for all 36 questions is genuinely more than this one card can finish, that is an acceptable, clearly-flagged outcome - do not silently ship a runner that only handles a subset without saying so in the completion report. Cover as many categories as you can get genuinely right; report exactly which remain, and why, rather than padding coverage with a fixture that doesn't actually test what its category claims.

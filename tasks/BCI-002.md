# BCI-002 — M1 first vertical slice (proposed, not started)

**Milestone:** M1 · **Week:** 2–3 · **Status:** proposed

## Scope (per Annex E.3)
"Published career record → explore → compare two options, on synthetic
fixtures." Exit proof required: real staging database and browser journey
pass; Annex D usability round 1 on the clickable prototype.

## Depends on (owner action — see docs/DECISIONS.md)
- A Supabase project (Mumbai region) — URL + publishable key + JWT secret
  in a real `.env` (never committed). If none exists yet, this is the
  first "owner action" item: create one, or say so and this slice targets
  a local Postgres instead until a real project is provisioned.
- Confirmation (or correction) of the pilot-state assumption (Gujarat) —
  doesn't block the *slice* itself (fixtures stay synthetic at M1), but
  blocks the *content track* running in parallel from writing real
  Gujarat-specific rules.

## Proposed breakdown
1. **Data foundation**: Supabase schema migration for `Source`, `Claim`,
   `Career`, `Pathway` (append-only migration file, per
   `docs/ARCHITECTURE.md`); RLS policies; restricted application role
   (never the owner/service role) — see `docs/SECURITY.md`.
2. **RLS tests** (`make test-db`): guest/student A/student B/reviewer ×
   read/write, run as the restricted role, not the DB owner.
3. **Explore screen**: list published Career records (synthetic fixtures
   seeded through the same publishing path a real record would use — no
   shortcut that lets fixtures skip maker-checker, even in dev).
4. **Compare screen**: two pathways side by side, fields per
   `docs/UI.md`'s comparison-field list (entry requirements, stages, time
   range, cost as three amounts, evidence with trust labels).
5. **Design track (parallel, Annex D.3)**: low-fidelity quick-start/
   explore/compare/plan flows; clickable prototype; usability round 1
   (5–8 participants) run *before* this slice's engines are considered
   done — not after.

## Exit proof to produce
- `make test-db` green against a real (staging) Postgres with RLS
  actually enforced (a cross-user read attempt must fail, verified by a
  test that asserts the failure, not just the absence of an error).
- A browser/HTTP walkthrough: seed → publish → explore → compare, entirely
  on labelled synthetic data.
- Usability round 1 notes against the six task criteria in
  `docs/UI.md`/Annex D.3.

## Reviewer invocations expected during this task
- `data-security-reviewer` once RLS policies and the publishing path exist.
- `ux-qa-reviewer` once explore/compare are reachable end to end.

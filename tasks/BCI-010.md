## What to build
Migration `db/migrations/0011_ai_usage.sql`. **Reserve the number at session open by running `ls db/migrations/` yourself first** - if anything newer than `0010_plan_actions.sql` already exists, stop and report rather than guessing a number.

Table `ai_usage`: `id uuid primary key default gen_random_uuid()`, `identity_kind text not null check (identity_kind in ('account','guest'))`, `identity_hash text not null` (a hash of the account id or guest-session token - never the raw identifier), `template_id text not null`, `calls_reserved int not null`, `calls_made int not null default 0`, `status text not null check (status in ('reserved','settled','failed'))`, `selection_ids uuid[]`, `verification_ids uuid[]`, `created_at timestamptz not null default now()`. **No prompt text column and no answer text column exist anywhere in this table - this is a hard requirement, not a style choice** (CLAUDE.md: no student data to development agents; this table is read by agents).

Two `SECURITY DEFINER` Postgres functions with an explicitly pinned `search_path` (mirror the pattern already used by this codebase's other definer functions - check an existing one, e.g. in `db/migrations/0003_maker_checker.sql`, for the exact style used here):
- `ai_reserve(p_identity_kind text, p_identity_hash text, p_template_id text, p_calls int)` - in one transaction, checks a per-identity daily cap, a global daily cap and a global monthly cap (read the cap values from a small `ai_usage_caps` config table you also create, one row, not hardcoded in the function body), and either inserts a `reserved` row and returns its id, or raises an exception the Python wrapper turns into a typed "budget exceeded" error. Must be safe under concurrent callers (use `for update` / an appropriate lock so two simultaneous reservations cannot both slip through a cap by one).
- `ai_settle(p_usage_id uuid, p_calls_made int, p_status text, p_selection_ids uuid[], p_verification_ids uuid[])` - updates the row to `settled` or `failed`.

RLS: a signed-in account can `select` only its own rows (matched on `identity_hash` derived from its own JWT - do not let a client supply `identity_hash` directly for a select; derive it server-side the same way `app/web/guest_session.py` or the JWT-based account lookup already does elsewhere in this codebase - check how an existing account-scoped table restricts `select` for the exact pattern to copy). A guest can never `select` any row (guests have no durable identity to check ownership against). A reviewer can `select` only an aggregate view with no identity column (`ai_usage_daily_totals` or similar - counts and totals only). No one but the two definer functions can `insert` or `update` `ai_usage` directly - deny both to `anon` and `authenticated` roles, grant `execute` on the two functions instead.

Python wrapper `app/ai/budget_db.py`: a class or functions with the exact same call shape as `app/ai/budget.py`'s `AIRequestBudget` (`reserve`, `remaining`), so a later card can swap the in-memory budget for this one by changing a single import - do not change `app/ai/budget.py` itself, and do not touch `app/core/config.py` or any other file outside your owned list.

Add the guest / student A / student B / reviewer rows for `ai_usage` (and the aggregate view) to `tests/db/access_matrix.py` in the same PR - this is required, not optional (CLAUDE.md: cross-user access is tested every time RLS changes; the lead does not merge a migration while this table is red).

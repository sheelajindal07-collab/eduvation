# BCI-005 — M4 maker-checker enforcement

**Milestone:** M4 · **Status:** DB-level enforcement AND the
publishing-console API built and tested; **migration not yet applied**
(owner action needed, same as 0002) — every route below 403s/400s until
then.

## Scope (docs/DATA.md "Publishing workflow"; CLAUDE.md non-negotiable)
"Every published fact has a source, a verification date and a verifier.
Unapproved facts never reach public results (maker-checker, enforced
server-side, not by a button)." `db/migrations/0001_init.sql`'s own
comment above `claims_update_reviewers` flagged this exact gap at M1 and
named the fix M4 would need — this task builds that fix.

## Why this, now
M2's three engines and M3's sign-in/saved-plans are built and wired into
live routes, but the actual maker-checker guarantee — the thing CLAUDE.md
lists first among its non-negotiables — has been sitting as a documented
gap since M1. Nothing currently stops a single reviewer from inserting a
claim directly as `published`, or approving their own draft. Orthogonal
to M3's guest-migration/consent work (a different table, `claims` not
`saved_plans`/`auth.users`), so it was picked up in parallel without
overlap.

## What shipped (2026-09-19)
- `db/migrations/0003_maker_checker.sql`:
  - **A trigger (`enforce_claims_workflow`), not just an RLS check**,
    because the immutability/transition rules need OLD vs NEW row
    comparison, which RLS's `using`/`with check` clauses can't express
    directly:
    - Every `INSERT` must be `status = 'draft'` — no direct-to-published
      or direct-to-in_review shortcut, from any client.
    - Valid transitions only: `draft ↔ in_review`, `in_review →
      published`. Any other jump (`draft → published` directly,
      anything from `superseded`) is rejected.
    - **The core guarantee**: `→ published` requires `reviewed_by` set
      AND distinct from `created_by` — the author of a claim cannot
      approve their own claim, enforced in the database, not by a UI
      button choosing not to show an "approve" button to the author.
    - **Published content is frozen**: once `published`, the only legal
      transition is to `superseded`, and only `status`/`superseded_by`
      may change — not `value`, `source_id`, `verification_date`, or
      authorship. A correction means inserting a *new* claim and
      pointing the old one's `superseded_by` at it (docs/DATA.md
      "Correction"), never an in-place edit of a fact that was already
      shown to a student as verified.
  - **`service_role` is exempt**, mirroring exactly what RLS already
    does for that role (docs/SECURITY.md: "the application never
    connects as the owner/service role for a user-facing request"). This
    is what lets every existing test fixture across the repo keep
    seeding pre-published claims directly via `admin_client` — the same
    trust tier RLS already grants that role, not a new or weaker
    carve-out.
  - `claims_update_reviewers` RLS policy tightened per 0001's own
    documented plan: `with check (is_reviewer() and (reviewed_by is
    distinct from created_by))` — defense in depth alongside the
    trigger, the same "belt and suspenders" pattern 0001 already uses
    for the synthetic-source-never-published guarantee.
  - `maker_checker_schema_version()`: a tiny marker function so the test
    suite (and `tests/db/conftest.py`'s existing skip-if-not-applied
    pattern) can detect whether this migration has landed yet, the same
    way `_saved_plans_table_exists()` does for 0002 — this migration
    adds no new table, so there's nothing to `select` from directly.
- **12 new live tests** (`tests/db/test_maker_checker.py`): insert-must-
  be-draft (including the service-role exemption, proving existing
  fixtures elsewhere in the repo are unaffected), self-approval rejected,
  publishing-without-a-reviewer rejected, the full
  draft→in_review→published cycle with two genuinely distinct reviewer
  accounts, sending a claim back from review to draft, the direct-
  publish-skip rejected, editing a published claim's value in place
  rejected, a real correction via supersede (inserting a replacement
  claim, confirming the old claim's own recorded value is untouched),
  and a superseded claim's finality.
- `tests/db/conftest.py`: extended with the same skip-if-not-applied
  pattern already used for 0002, plus a `second_reviewer` fixture (the
  existing `reviewer` fixture is function-scoped — requesting it twice
  under different names would give the *same* account, useless for
  testing "a different person reviews").
- 163 tests total (92 unit + 46 live DB passing + 25 live DB tests
  correctly skipping until the migration is applied — verified with
  `pytest --collect-only`), lint/typecheck clean.

## Publishing-console API (2026-09-19)
- `app/api/claims.py`: `POST /claims`, `/claims/{id}/submit`,
  `/claims/{id}/approve`, `/claims/{id}/reject`, `/claims/{id}/supersede`,
  `GET /claims`. Reviewer-only, enforced by RLS + the trigger above —
  this layer does no access-control decision of its own (same "one place
  access rules live" principle as `compare.py`/`plans.py`). What it does
  own: `created_by`/`reviewed_by` are always the caller's own resolved
  user id (`session.client.auth.get_user(jwt=...)`, same pattern as
  `plans.py`'s `_current_user_id`) — **never** a client-supplied value.
  This is exactly the "known limitation" below, closed for real usage
  even though the DB layer alone still permits a caller-supplied
  `created_by` (kept at the DB layer for now — see below).
  - `POST /claims` always inserts `status='draft'`, never accepting it
    from the caller, and validates `extracted_by` as a pydantic
    `Literal["human", "ai"]` (a clean 422 instead of a raw Postgres
    constraint-violation relay) and rejects a literal `verifier="ai"`
    (docs/DATA.md: "a person's identifier — never 'ai'").
  - Every Postgres error the trigger/RLS can raise is mapped once, in
    one place (`_raise_for_claims_error`): RLS violation → 403, a
    nonexistent `source_id` → 404, the trigger's own workflow/
    self-approval/immutability message → 400 with that message relayed
    as-is (it's already reviewer-facing text, same reasoning
    `auth.py` uses for Supabase's own auth error text).
  - `GET /claims` defaults to `status=draft,in_review` (the actual
    review queue) — pass `?status=published` etc. explicitly for
    anything else. RLS still decides visibility: a non-reviewer gets an
    empty list for anything but published, never an error revealing
    drafts exist.
- **12 new live tests** (`tests/db/test_api_claims.py`): create/reject/
  guest-403/non-reviewer-403, invalid `extracted_by` → 422, literal
  `verifier="ai"` → 422, nonexistent source → 404, the full
  draft→submit→approve cycle with two distinct reviewer accounts through
  the *real* HTTP layer (not just the trigger directly, mirroring
  `test_maker_checker.py`'s coverage one layer up), self-approval
  rejected through the API, draft-skips-published rejected, reject
  sends back to draft, a real correction via supersede, and the
  review-queue listing correctly showing/hiding drafts by reviewer
  status.
- One transient test failure hit and confirmed non-recurring:
  `test_sign_up_new_email_succeeds_or_requires_confirmation` failed once
  under the full combined suite's load (plausibly Supabase Auth
  rate-limiting many real sign-ups in one run), passed in isolation and
  on a full re-run — not a regression from this task's changes, not
  silently ignored either.

## Not done yet (remaining scope)
- **Migration not yet applied** — needs the owner to run
  `db/migrations/0003_maker_checker.sql` via the SQL Editor (or
  `scripts/apply_migrations.py` if `DATABASE_URL` is set), same as 0002.
  Deliberately not applied by any agent — docs/DECISIONS.md: schema
  changes go through the owner's own project, never an agent's
  management-API access, even though a Supabase MCP tool is technically
  available in this session. **None of `app/api/claims.py` has been
  exercised against real data yet** — every one of its 12 tests is
  currently a skip, not a pass, until this lands. Re-run
  `pytest tests/db/test_maker_checker.py tests/db/test_api_claims.py -v`
  once it's applied and don't treat this task as verified until that's
  actually green.
- **`created_by = auth.uid()` is still not enforced at the database
  level** — the API now always sets it correctly for real traffic
  through this route, but nothing stops a direct table write (bypassing
  this API, e.g. from a future second client) from lying about it.
  Hardening this at the DB layer (`alter column created_by set default
  auth.uid()` plus a trigger check rejecting a mismatched caller-supplied
  value) is still real future work, tracked here as before, now lower
  urgency since the one real client that exists enforces it correctly.
- No rejection-reason field (schema has nowhere to put one yet).
- No pagination/sorting on `GET /claims` — fine at pilot scale (a
  handful of reviewers, tens of records), not fine at real content
  volume.
  check rejecting a caller-supplied value that doesn't match.
- **Cache invalidation and flagging affected saved plans on a
  correction** (docs/DATA.md point 4) — explicitly application-level,
  out of this task's DB-enforcement scope.
- AI-authored draft (`extracted_by = 'ai'`) handling: the schema already
  has the column and the "never published directly" property already
  holds (an AI-authored row must still go through the same
  draft→in_review→published cycle as anything else, and still needs a
  human `reviewed_by` distinct from `created_by`) — no additional
  AI-specific trigger logic was needed for this to already be true.

## What to build
`scripts/ai_translate_drafts.py` (new): an offline, owner-run script (never called from a request path, never imported by `app/`) that reads `app/i18n/en.json` (57 keys as of this card - read the real file, do not guess its shape) and `app/i18n/hi.json`, finds every key present in `en.json` but missing from `hi.json`, and for each one runs a **translation pass** (one `provider.generate(...)` call: English text in, a proposed Hindi translation out) followed by a **back-translation check pass** (a second, separate `provider.generate(...)` call: the proposed Hindi translation in, an English back-translation out - a different provider call, not a re-run of the first). Compare the back-translation against the original English by a simple, documented heuristic (your choice - e.g. a normalised token-overlap ratio above a threshold you pick and justify in the module docstring; do not claim semantic equivalence you cannot actually check with a cheap heuristic - be honest in the output about what "agreement" here does and does not mean).

Writes `content/staging/hindi_drafts/<run-date>.csv` (columns: `key`, `english`, `hindi_draft`, `back_translation`, `agreement_flag`, `agreement_score`) for a human Hindi reviewer to read - this script **never writes `hi.json` directly** and **never writes to the database**. Use `app/ai/gemini_provider.py`/`app/ai/adapter.py`/`app/ai/mock_provider.py` (already merged - read them for the real interface) for the provider calls, injectable so the script is testable with `MockAIProvider` and a `--provider mock` flag for CI; the real provider path needs the owner's key from the environment, exactly like every other AI-1a script, and is never exercised in a test.

A disagreement between the two passes (a low agreement score) is flagged in the output row, never silently dropped or silently accepted - the whole point of the CSV is that a human reads every row, agreeing or not.
